# AST-LLMベース画像生成VM 統合設計書 v0.1

作成: 2026-10-29
位置づけ: 恵一さんのGitHub（bluefox32）にある既存部品を、VMアプローチで画像生成システムとして統合するための設計案。確認済みの事実と設計判断を分けて記す。

---

## 1. 目的

- 既存のイラスト生成AI（Replit、フロント側distのみ現存）は「生成して保存する」一方通行の構成だった。
- 本設計は、自分のリポジトリ群にある検証可能な部品を組み合わせ、**生成 → 測定 → 評価 → 調整して再実行**が回るVMとして組み直すことを目的とする。
- 画像を描くエンジン自体は新規に接続する（既存部品には存在しないため）。設計の独自性は、制御・解析・評価・記録の層に置く。

## 2. 確認済みの前提（事実）

| 対象 | 確認内容 |
|---|---|
| AST-LLM | 約900行、Pure Python + NumPyのみ。プロンプト→AST解析→変換パイプライン（冪等性・不変条件チェック）→ベクトル化→Attention検索→応答再構成。ハッシュチェーンによる改ざん検知付き。**画像生成機構は無い** |
| VMA-protocol | zip 2点のみ収録。実体は「VMA Quantum」：量子ビット判定（連続スコア＋忠実度＋閾値判定）、ブロッホ差分圧縮（往復検証付き符号化）、拡張量子FX（ノルム保存チェック）を、Flask REST API＋クライアントとしてオフロード配布する構成。実計算はNumPy上の古典シミュレーション。**VMの骨格ではない** |
| VMAの文書差異 | 統合レポートの圧縮例（kp=42→m=84）は同梱コード（m=172）と一致しない。レポート記載の提供物3点（codec_double_decode_optimized.py、VMA_TEST_REPORT.md、requirements-dev.txt）はzip内に無い |
| その他候補部品 | 58リポジトリの一覧と主要候補のREADMEを確認済み（下表）。いずれも単一ファイル級の実験コード |
| ライセンス | 全リポジトリMIT（権利者 bluefox32 に統一済み）。組み合わせに法的障害なし |

## 3. 設計原則

1. **VMとして組む** — 状態（レジスタ／メモリ）、命令（変換パス）、実行、入出力を分離し、1回の生成を「命令列の実行」として扱う。
2. **実測に anchored する** — スコアは測定可能な量（RGB統計、周波数成分、ベクトル距離）から作る。測定できない指標は採用しない。
3. **コードと実測を正とする** — ドキュメントの数値・主張は鵜呑みにしない（VMAの文書差異の教訓）。各部品は取り込み時に動作テストを通す。
4. **疎結合・差し替え可能** — 部品間はAPI境界（VMA 104 のオフロード形態が実働見本）で分離する。画像エンジンもアダプタ越しに差し替え可能にする。
5. **本体の純度を守る** — AST-LLM本体は「900行以下・NumPyのみ」の維持条件があるため触らず、固定版を部品としてimportする。新規コードは派生側に置く。
6. **来歴と巻き戻し** — 全ステップをハッシュチェーンに記録し、任意の回の状態へロールバックできるようにする。

## 6. VM仕様案

### 6.1 状態（レジスタ／メモリ相当）

| 状態項目 | 内容 |
|---|---|
| PROMPT_AST | AST-LLMで構造化したプロンプト（主題／画風／構図／除外要素のノード） |
| SEED | 生成シード。再現性のため必須記録 |
| SIZE | 許可値のみ（例: 1024x1024）。不変条件で検証 |
| STYLE | 既存アプリ互換の vivid / natural 等、列挙型 |
| PALETTE_VEC | 目標パレットを正規化したベクトル（create-standard-colors- の基準で正規化） |
| STYLE_VEC | 画風ベクトル。New_matrix方式で加算合成・巻き戻し可能に |
| TARGETS | スコア目標値と閾値 |
| ITER / COST | 反復回数と累積コスト（API費用・時間）。上限を不変条件に |
| HISTORY_HEAD | ハッシュチェーンの先頭。状態分岐とロールバックの起点 |

### 6.2 命令（変換パスとして実装）

```text
PARSE          プロンプト → PROMPT_AST
VALIDATE       不変条件チェック（サイズ、スタイル、矛盾指定、コスト上限）
COMPILE        AST → エンジン用プロンプト＋パラメータセット（往復検証付き符号化）
GEN            画像エンジン呼び出し（アダプタ経由）
ANALYZE_RGB    RGB統計・色分布の測定
ANALYZE_FFT    周波数指標の測定
ANALYZE_VEC    Σブロックベクトル抽出、参照との距離計算
SCORE          指標 → 総合スコア（回帰）＋ 合格／再試行判定
ADJUST         差分ベクトルから PALETTE_VEC / STYLE_VEC / プロンプトを調整
COMMIT         保存層へ記録＋ハッシュチェーンへ追加
ROLLBACK       指定した回の状態へ復帰
```

各命令はAST-LLMの変換パスの流儀に従い、**冪等性と不変条件チェックを必須**とする（解析系命令は同じ入力に同じ結果を返すこと、等）。

### 6.3 1生成サイクル

```text
PARSE → VALIDATE → COMPILE → GEN
  → ANALYZE_RGB / ANALYZE_FFT / ANALYZE_VEC
  → SCORE
      ├─ 合格 → COMMIT → 終了
      └─ 再試行 かつ ITER・COST が上限内 → ADJUST → GEN へ戻る
      └─ 上限到達 → 最良の回を COMMIT して終了（打ち切りを記録）
```

## 7. スコア設計（測定可能なものだけを使う）

| 指標 | 測定方法 | 基準 |
|---|---|---|
| 色一致度 | 生成画像の色分布と PALETTE_VEC の距離（正規化後の色空間で計算） | create-standard-colors- の正規化（sRGBガンマ、高ビット深度の扱い） |
| 精細度 | FFTによる高周波エネルギー比 | 同一サイズ・同一条件の参照生成群との相対比較 |
| 特徴類似度 | Σブロックベクトルと参照画風ベクトルのコサイン類似度 | AST-LLM の Attention（内積スコア＋softmax）の流儀で重み付け |
| 総合スコア | 上記指標から回帰で算出（Extecped-values-AI-algorithms- 方式） | 人間評価データで較正するまでは「仮スコア」と表示を分ける |
| 判定 | 総合スコア＋信頼度（測定の安定性）＋閾値で、合格／再試行を判定 | VMA judge の「連続値＋忠実度＋判定」の形式を借用 |

注記: 既存アプリの quality score は計算方法が未検証（dist 側に含まれず）。本設計では計算方法を公開可能な形で定義し直す。

## 8. 保存層（DB）設計案

SQLite-Multiple-DB の方式（圧縮DB群＋master管理＋インメモリ展開＋監査ログ＋SHA256検証）を土台にする。

| テーブル（論理） | 主な内容 |
|---|---|
| generations | 生成ID、PROMPT_AST（JSON）、SEED、SIZE、STYLE、エンジン名と版、生成日時 |
| runs | 生成ID、ITER、各回のパラメータ差分（ADJUST履歴）、コスト |
| images | 画像本体（圧縮保存）またはファイル参照、SHA256 |
| analyses | 生成ID＋回、RGB統計、FFT指標、Σベクトル（符号化して保存） |
| scores | 指標一式、総合スコア、判定、較正モデルの版 |
| audit | 全操作の監査ログ（master側） |

設計上の決め事:

- **スキーマは版管理する**。「DB構造に傾向が反映される」という以前の仮説を検証可能にするため、スキーマ変更は理由とともに履歴に残す。（2026-10-29 実装済み: `store.py` の SCHEMA_HISTORY と DB内 `schema_versions` テーブルで運用開始、現在 v1。ユーザーが重点管理項目として指定）
- 画像と解析結果は分離する。解析は後から再計算できるが、生成条件（AST、シード、版）の記録が無ければ再現できないため、そちらを必須とする。

## 9. 画像エンジン・アダプタ

| 方式 | 利点 | 欠点 | 本設計での扱い |
|---|---|---|---|
| API型（OpenAI等） | 品質が安定、GPU不要、既存アプリと同方式 | 生成ごとに費用、外部依存 | 後付け候補。同一アダプタIFで追加可能にする |
| ローカルSD型（diffusers / ComfyUI） | 従量費用なし、パラメータ自由度が高い | GPU環境が必要、運用が重い | **第1実装（2026-10-29 決定）**。実装はコードから制御できる diffusers を基本とする |
| 自前モデル学習 | 独自性は最大 | データと計算資源が別規模 | 本設計の範囲外（LoRA等の追加学習は将来候補） |

アダプタIFは「パラメータセット（プロンプト、サイズ、スタイル、シード）→ 画像＋実測メタデータ（所要時間、費用）」に統一する。

## 11. リスクと未検証事項

- **部品の実働は未検証**: 今回の確認は一覧・README・一部コード（AST-LLM、VMA）まで。CELL、CUDA系、SQLite系などは取り込み時に個別の動作テストが必須。
- **文書とコードの乖離**: VMAで実例を確認済み。全般に「READMEの数値は未実測」と扱う。
- **依存の混在**: OpenCV、Numba/CUDA、scikit-learn、trimesh、Flask、SymPyなど。プロセス／API境界で分離し、必須依存を増やさない。
- **スコアの妥当性**: 指標が「測定可能」でも「良い絵」と相関するとは限らない。フェーズ4の較正までは総合スコアを根拠に順位付けしない。
- **配置先**: Replitの新規作成はサブスクリプション制約で停止した実績がある。ソースの置き場所はGitHubの派生リポジトリを第1候補とし、実行環境は分けて決める。

## 12. 決定事項と保留事項

### 決めたこと（本設計の前提）

- ベースはAST-LLM（制御・評価層）。本体は改変しない。
- 画像エンジンはアダプタ越しに接続する。第1実装はローカルSD型（diffusers）とする（2026-10-29 決定）。API型は同じアダプタIFで後付け可能に保つ。
- VMA-protocolは「判定形式・符号化の検証方式・API配布形態」の借用に留め、VM骨格にはしない。
- 保存はSQLite-Multiple-DB方式、状態履歴はMulti-layer-hash-chain方式を土台にする。
